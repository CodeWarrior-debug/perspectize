# Content type spec: YouTube Music track

Generated by `tools/content-type-designer`. Every line below is a decision that was made in the form — nothing here was inferred by a model.

## 1. Identity

| Decision | Value |
| --- | --- |
| Label | YouTube Music track |
| Plural | YouTube Music tracks |
| GraphQL / domain enum | `YOUTUBE_MUSIC` |
| DB value (lowercased by the mapper) | `youtube_music` |
| What one row is | A song streamed through YouTube Music, resolved to its MusicBrainz recording (ISRC) where one exists. |
| Type icon | note |
| Accent colour | #FF3355 |

## 2. Ingestion & enrichment

| Decision | Value |
| --- | --- |
| Ingestion method | api |
| Enrichment source | ytmusicapi (unofficial InnerTube endpoints — no official YouTube Music Data API) for track/artist/album lookup, cross-referenced against MusicBrainz for ISRC + Cover Art Archive artwork |
| URL required | yes |
| Accepted URL shapes | music.youtube.com/watch?v=<id> (also accepts youtube.com/watch?v=<id> when the video is a recognised YT Music track) |
| Natural identity / dedup key | ISRC via MusicBrainz cross-reference (fallback: YouTube Music videoId, then artist + title + album) |
| Cross-type URL uniqueness | MUST relax the global `UNIQUE(url)` constraint — this type can share a URL with another type. Migration required: replace with `UNIQUE(url, content_type)` or a partial index. |
| Thumbnail strategy | YouTube Music thumbnail (i.ytimg.com), replaced by Cover Art Archive front image once ISRC resolves |

Adapter to build: `backend/internal/adapters/youtube_music/` (`client.go`, `parser.go`) behind a port interface in `backend/internal/core/ports/services/`, wired in `cmd/server/main.go`.

### Mixed-unit sort policy

Sorting any of these columns on its own would order numbers that mean different things. The grid must not do it silently: when one becomes the *primary* sort key, show an alert and leave the order unchanged until the user picks one of:

1. **Filter to one type** — one button per type, each named with its unit; the sort then applies within one unit.
2. **Sort by Type, then the column** — a multi-column sort with the unit-consistent Type column as priority 1, so each type is ordered within its own unit.

## 6. Consistency review

- **NOTE** (`creator`): "Creator" stands in for Artist / Channel — keep the per-type label in the cell tooltip.
- **NOTE** (`length`): "Length" mixes units across types (seconds → m:ss | seconds → h:mm:ss). Format per row from length_units. Sorting it alone raises the mixed-unit alert: filter to one type, or sort by Type first and "Length" second.
- **NOTE** (`date`): "Date" stands in for Released / Published — keep the per-type label in the cell tooltip.
- **MUST FIX** (`audience`): YouTube video marks "Views" required, but the column is hidden for this selection. Either relax it to typical or pin the column when that type is in the filter.

## 8. Testing approach

Mock ytmusicapi responses for: (1) a track that resolves an ISRC via MusicBrainz, (2) one that never resolves one (falls back to videoId identity), (3) a duration mismatch between YT Music and the MusicBrainz recording (assert we keep the YT Music duration for display and the MusicBrainz one only for match confidence). Cover the identity fallback chain end-to-end since it is the whole rationale for this type.

## 9. Conventions to ignore for this work only

Enrichment source (ytmusicapi) is unofficial and unversioned — no API key, no SLA, no ToS coverage. Every other api-ingestion type in the catalog (YouTube Data API v3, TMDB, Open Library, iTunes Search, MusicBrainz) is an official or fully open, keyless source. This type is a deliberate exception and should be flagged as higher-maintenance-risk in review, not treated as equivalent in reliability to youtube or music.
