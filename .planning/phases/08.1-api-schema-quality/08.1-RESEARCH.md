# Phase 8.1: API & Schema Quality - Research

**Researched:** 2026-02-16
**Domain:** GraphQL schema quality, gqlgen scalar types, GORM constraints, Go input validation
**Confidence:** HIGH

## Summary

Phase 8.1 fixes 10 API quality issues spanning GraphQL schema types, database constraints, and input validation. The primary challenges are: (1) migrating timestamps from `String!` to `DateTime` scalar, (2) enforcing uniqueness at the database level instead of application-level checks, (3) extracting structured YouTube data instead of storing raw JSON blobs, and (4) implementing comprehensive input validation.

**Current State:**
- GraphQL schema uses `String!` for timestamps and `contentType` (lines 18-19, 63-64, 77, 90-91 in schema.graphql)
- User and content uniqueness checked with read-then-write pattern in services (user_service.go:60-78, no DB constraints in GORM models)
- YouTube API response stored as raw JSON blob in `response` field (youtube/client.go:102, schema.graphql:89)
- Perspective nested resolvers (`user`, `content`) not implemented — fields return null (M-08)
- No input validation on description, labels, parts, categorizedRatings (M-11)
- Update operations don't check `RowsAffected` for optimistic concurrency (M-16 in perspective_repository.go:54-63)

**Primary recommendation:** Use gqlgen's built-in `Time` scalar, add GORM `uniqueIndex` tags, parse YouTube response into structured fields, implement field resolvers for nested types, use go-playground/validator for input validation, and check `RowsAffected` in Update operations.

## Architecture Patterns

### Recommended GraphQL Schema Evolution Pattern

**Approach:** Non-breaking additive migration for timestamp fields.

```graphql
# Before (schema.graphql:18-19, 63-64, 90-91)
type User {
  createdAt: String!
  updatedAt: String!
}

# After (recommended)
scalar Time  # Built-in gqlgen scalar

type User {
  createdAt: Time!   # New field, proper type
  updatedAt: Time!
  # Deprecated fields can be removed in breaking change
}
```

**Why Time not DateTime:** gqlgen's built-in `Time` scalar maps to Go's `time.Time` and serializes to RFC3339Nano format. This is the standard GraphQL DateTime representation.

**Source:** [gqlgen scalars documentation](https://gqlgen.com/reference/scalars/) confirms: "Built-in scalars: Time adheres to the time.RFC3339Nano format."

### Pattern 2: GORM Unique Constraints

**What:** Use `uniqueIndex` struct tags to enforce DB-level uniqueness.

**When to use:** Preventing duplicate username/email (H-06, H-07 race conditions).

**Implementation:**
```go
// gorm_models.go (current: no unique tags)
type UserModel struct {
    ID        int       `gorm:"primaryKey;autoIncrement"`
    Username  string    `gorm:"not null;uniqueIndex"`           // Add uniqueIndex
    Email     string    `gorm:"not null;uniqueIndex"`           // Add uniqueIndex
    // ...
}
```

**Migration approach:**
```sql
-- Migration to add constraints
ALTER TABLE users ADD CONSTRAINT users_unique_username UNIQUE (username);
ALTER TABLE users ADD CONSTRAINT users_unique_email UNIQUE (email);
```

**Service layer changes:**
```go
// user_service.go:60-78 (remove read-then-write checks)
// Before:
existing, err := s.repo.GetByUsername(ctx, username)
if err == nil && existing != nil {
    return nil, fmt.Errorf("%w: username already taken", domain.ErrAlreadyExists)
}

// After (let DB constraint handle it):
created, err := s.repo.Create(ctx, user)
if err != nil {
    // Check for unique violation error
    if isUniqueViolation(err) {
        return nil, fmt.Errorf("%w: username or email already taken", domain.ErrAlreadyExists)
    }
    return nil, err
}
```

**Unique violation detection:**
GORM doesn't provide a standard error type for unique violations ([Issue #6002](https://github.com/go-gorm/gorm/issues/6002)). Use database-specific error checking:

```go
// PostgreSQL unique violation error code: 23505
func isUniqueViolation(err error) bool {
    var pgErr *pgconn.PgError
    if errors.As(err, &pgErr) {
        return pgErr.Code == "23505" // unique_violation
    }
    return false
}
```

**Source:** [GORM indexes documentation](https://gorm.io/docs/indexes.html) — `uniqueIndex` tag creates single-column unique constraints.

### Pattern 4: Field Resolvers for Nested Types

**What:** Implement field resolvers for `Perspective.user` and `Perspective.content`.

**When to use:** When GraphQL schema has nested object references (M-08).

**Current state:**
Schema defines nested fields (schema.graphql:48-50):
```graphql
type Perspective {
  user: User       # Returns null - no resolver
  content: Content # Returns null - no resolver
}
```

**Implementation:**
```go
// schema.resolvers.go - Add field resolvers
func (r *perspectiveResolver) User(ctx context.Context, obj *model.Perspective) (*model.User, error) {
    userID, err := strconv.Atoi(obj.UserID)
    if err != nil {
        return nil, fmt.Errorf("invalid user ID: %w", err)
    }

    user, err := r.UserService.GetByID(ctx, userID)
    if err != nil {
        if errors.Is(err, domain.ErrNotFound) {
            return nil, nil
        }
        return nil, err
    }

    return userDomainToModel(user), nil
}

func (r *perspectiveResolver) Content(ctx context.Context, obj *model.Perspective) (*model.Content, error) {
    if obj.ContentID == nil {
        return nil, nil
    }

    contentID, err := strconv.Atoi(*obj.ContentID)
    if err != nil {
        return nil, fmt.Errorf("invalid content ID: %w", err)
    }

    content, err := r.ContentService.GetByID(ctx, contentID)
    if err != nil {
        if errors.Is(err, domain.ErrNotFound) {
            return nil, nil
        }
        return nil, err
    }

    return domainToModel(content), nil
}

// Add resolver type
type perspectiveResolver struct{ *Resolver }

func (r *Resolver) Perspective() generated.PerspectiveResolver {
    return &perspectiveResolver{r}
}
```

**Source:** [gqlgen resolvers documentation](https://gqlgen.com/reference/resolvers/) — Field resolvers execute concurrently when nested fields are queried.

### Pattern 5: Input Validation with go-playground/validator

**What:** Validate input lengths for description, labels, parts, categorizedRatings (M-11).

**When to use:** All mutation inputs that accept unbounded strings or slices.

**Implementation:**
```go
// perspective_service.go - Add validation
import "github.com/go-playground/validator/v10"

type PerspectiveService struct {
    repo     repositories.PerspectiveRepository
    userRepo repositories.UserRepository
    validate *validator.Validate
}

func NewPerspectiveService(repo, userRepo) *PerspectiveService {
    return &PerspectiveService{
        repo:     repo,
        userRepo: userRepo,
        validate: validator.New(),
    }
}

// Define validated input struct
type CreatePerspectiveValidated struct {
    Description        *string                `validate:"omitempty,max=5000"`
    Labels             []string               `validate:"omitempty,max=50,dive,max=100"`
    Parts              []int                  `validate:"omitempty,max=100,dive,min=0"`
    CategorizedRatings []domain.CategorizedRating `validate:"omitempty,max=50,dive"`
}

func (s *PerspectiveService) Create(ctx context.Context, input portservices.CreatePerspectiveInput) (*domain.Perspective, error) {
    // Validate input
    validated := CreatePerspectiveValidated{
        Description:        input.Description,
        Labels:             input.Labels,
        Parts:              input.Parts,
        CategorizedRatings: input.CategorizedRatings,
    }

    if err := s.validate.Struct(validated); err != nil {
        return nil, fmt.Errorf("%w: %v", domain.ErrInvalidInput, err)
    }

    // ... rest of create logic
}
```

**Dive tag explanation:** `dive` tells validator to validate each element of a slice/array. Example: `"max=50,dive,max=100"` means "max 50 items, each item max 100 chars".

**Source:** [go-playground/validator documentation](https://github.com/go-playground/validator) — Supports slice diving for nested validation.

### Pattern 6: RowsAffected Check for Optimistic Concurrency

**What:** Check `result.RowsAffected` in Update operations to detect TOCTOU races (M-16).

**When to use:** All repository Update methods.

**Current state (perspective_repository.go:54-63):**
```go
func (r *GormPerspectiveRepository) Update(ctx context.Context, p *domain.Perspective) (*domain.Perspective, error) {
    model := perspectiveDomainToModel(p)

    if err := r.db.WithContext(ctx).Save(model).Error; err != nil {
        return nil, fmt.Errorf("failed to update perspective: %w", err)
    }
    // No RowsAffected check - M-16

    return r.GetByID(ctx, model.ID)
}
```

**Fixed version:**
```go
func (r *GormPerspectiveRepository) Update(ctx context.Context, p *domain.Perspective) (*domain.Perspective, error) {
    model := perspectiveDomainToModel(p)

    result := r.db.WithContext(ctx).Save(model)
    if result.Error != nil {
        return nil, fmt.Errorf("failed to update perspective: %w", result.Error)
    }

    if result.RowsAffected == 0 {
        return nil, domain.ErrNotFound
    }

    return r.GetByID(ctx, model.ID)
}
```

**Note:** Delete already implements this pattern (perspective_repository.go:67-78).

**Source:** [GORM update documentation](https://gorm.io/docs/update.html) — `result.RowsAffected` provides count of updated records.

## Don't Hand-Roll

Problems that look simple but have existing solutions:

| Problem | Don't Build | Use Instead | Why |
|---------|-------------|-------------|-----|
| DateTime serialization | Custom RFC3339 marshaler | gqlgen `Time` scalar | Built-in, tested, RFC3339Nano format |
| Unique constraint violation detection | String matching on error messages | PostgreSQL error code 23505 | Database-agnostic error codes unreliable in GORM |
| Input validation | Manual length checks | go-playground/validator | Handles edge cases (UTF-8, max bytes vs chars) |
| Cursor pagination | Custom encoding | gorm-cursor-paginator | Already integrated in Phase 7.2 |

**Key insight:** GraphQL scalars, DB constraints, and validation libraries handle edge cases (timezones, race conditions, Unicode) that manual implementations miss.

## Common Pitfalls

### Pitfall 1: Breaking GraphQL Schema Changes
**What goes wrong:** Changing `createdAt: String!` to `createdAt: Time!` breaks existing clients expecting string format.

**Why it happens:** GraphQL has no built-in versioning — all clients share one schema.

**How to avoid:**
1. Add new field with correct type: `createdAtTime: Time!`
2. Mark old field deprecated: `createdAt: String! @deprecated(reason: "Use createdAtTime")`
3. Dual-write both fields during migration
4. Remove deprecated field in next major version

**Warning signs:** Frontend GraphQL queries start failing after backend deployment.

**Source:** [GraphQL versioning guide](https://oneuptime.com/blog/post/2026-01-24-graphql-api-versioning/view) — Use additive changes and deprecation for evolution.

**Alternative (acceptable for this project):** Since this is pre-production with no external clients, breaking change is acceptable. Document in migration notes.

### Pitfall 2: GORM AutoMigrate Doesn't Add Constraints to Existing Columns
**What goes wrong:** Adding `uniqueIndex` tag to existing field doesn't create DB constraint with `AutoMigrate()`.

**Why it happens:** GORM's AutoMigrate only adds constraints when creating tables, not when modifying existing columns ([Issue #4110](https://github.com/go-gorm/gorm/issues/4110)).

**How to avoid:** Write explicit SQL migration for constraint addition:
```sql
ALTER TABLE users ADD CONSTRAINT users_unique_username UNIQUE (username);
```

**Warning signs:** Duplicate username inserts succeed despite `uniqueIndex` tag.

### Pitfall 3: Time Zone Handling in DateTime Scalars
**What goes wrong:** Storing timestamps without timezone, comparing local time to UTC, displaying wrong time to users.

**Why it happens:** Go's `time.Time` includes timezone, but serialization/deserialization can lose it.

**How to avoid:**
- Use `time.Time` throughout (includes zone info)
- gqlgen Time scalar serializes to RFC3339Nano with zone offset
- PostgreSQL `timestamptz` stores UTC with offset

**Warning signs:** Times off by timezone offset (e.g., 7 hours for PST).

### Pitfall 4: Validation on Pointer Fields
**What goes wrong:** Validator skips nil pointer fields, allowing unbounded input.

**Why it happens:** `omitempty` tag treats nil as "don't validate".

**How to avoid:** Validate before passing to service, or use `required` when appropriate:
```go
Description *string `validate:"omitempty,max=5000"`  // Validates if present
Labels      []string `validate:"required,max=50"`     // Must exist, validates always
```

**Warning signs:** Nil description field bypasses max length validation.

### Pitfall 5: N+1 Query Problem with Field Resolvers
**What goes wrong:** Fetching list of 100 perspectives triggers 100 separate user queries (one per perspective).

**Why it happens:** Field resolvers execute per item without batching.

**How to avoid:** Use [dataloader pattern](https://gqlgen.com/reference/dataloaders/) to batch queries.

**Warning signs:** Slow GraphQL queries, database connection pool exhaustion.

**For this phase:** Document as future optimization. Field resolvers are correct starting point.

## State of the Art

| Old Approach | Current Approach | When Changed | Impact |
|--------------|------------------|--------------|--------|
| Application-level uniqueness checks | DB constraints with error handling | 2024+ | Eliminates race conditions, simpler code |
| Custom DateTime scalars | gqlgen built-in Time scalar | gqlgen v0.17+ | Less code, standard RFC3339Nano format |
| Raw JSON storage | Structured fields | Modern practice | Better queryability, reduced storage |
| Manual validation | go-playground/validator | v10+ (2020+) | Handles Unicode edge cases, less boilerplate |

**Deprecated/outdated:**
- **String timestamps in GraphQL:** Modern schemas use DateTime/Time scalars (RFC3339 format)
- **Read-then-write uniqueness checks:** Database constraints prevent TOCTOU races
- **Storing full API responses:** Parse and store only needed fields (privacy, storage efficiency)

## Open Questions

1. **Breaking change strategy for timestamp fields**
   - What we know: Changing `String!` to `Time!` is breaking for existing clients
   - What's unclear: Accept breaking change (pre-production) or dual-field migration?
   - Recommendation: Breaking change acceptable — project is pre-production with no external clients. Document in PLAN.md.

2. **Validation error message format**
   - What we know: go-playground/validator returns structured errors
   - What's unclear: How granular should GraphQL error responses be? (field-level vs general "invalid input")
   - Recommendation: Return general error for now, consider field-level errors in future UX phase.

3. **N+1 query mitigation timeline**
   - What we know: Field resolvers will cause N+1 queries for perspective lists
   - What's unclear: Is performance acceptable for current scale (~100 perspectives)?
   - Recommendation: Implement basic resolvers now, add dataloader if performance testing shows issues.
