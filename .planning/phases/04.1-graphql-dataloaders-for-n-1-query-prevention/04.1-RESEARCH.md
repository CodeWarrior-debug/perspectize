## Summary

This phase implements the Facebook DataLoader pattern to eliminate N+1 SQL queries from three nested GraphQL relationships. The current state is that `Perspective.user`, `Perspective.content`, and `Content.addedBy` fields exist in the generated `model.Perspective` and `model.Content` structs but always resolve to `nil` — no field resolvers exist for them. Without dataloaders, a `perspectives(first: 50) { items { user { name } content { name } } }` query would execute 1 + 50 + 50 = 101 SQL queries.

The implementation requires four coordinated changes: (1) add `GetByIDs` batch methods to `UserRepository` and `ContentRepository` port interfaces and their GORM implementations, (2) create a `loaders` package in the GraphQL adapter layer with `UserLoader` and `ContentLoader` backed by those batch methods, (3) configure gqlgen field resolver directives in `gqlgen.yml` and regenerate code to get `perspectiveResolver` and `contentResolver` types, and (4) wire per-request middleware into the chi router so each GraphQL request gets fresh loader instances injected into context.

The chosen library `vikstrous/dataloadgen` v0.0.10 (released August 6, 2025) uses Go generics to eliminate code generation, is recommended by the official gqlgen documentation, and benchmarks faster than alternatives. The `NewMappedLoader` variant is recommended over `NewLoader` because GORM's `WHERE id IN` results may return in arbitrary order, and mapped fetch handles ordering automatically while also providing built-in `ErrNotFound` for missing keys.

**Primary recommendation:** Use `NewMappedLoader` with a GORM `WHERE id IN` query for both batch functions; place loaders in `internal/adapters/graphql/loaders/` to stay within the adapter layer per hexagonal architecture rules.

## Architecture Patterns

### Recommended Project Structure

```
backend/internal/adapters/graphql/
├── loaders/
│   └── loaders.go           # Loaders struct, NewLoaders, Middleware, For(), GetUser(), GetContent()
├── resolvers/
│   ├── resolver.go          # Resolver struct (add Loaders field or use context only)
│   ├── schema.resolvers.go  # Existing query/mutation resolvers
│   ├── perspective.resolvers.go  # NEW: perspectiveResolver field resolvers (generated by gqlgen)
│   ├── content.resolvers.go      # NEW: contentResolver field resolvers (generated by gqlgen)
│   └── helpers.go           # Existing domain-to-model converters
```

The `loaders` package lives inside `adapters/graphql/` — it is infrastructure code (batching network/DB calls), not domain logic. This respects the hexagonal architecture dependency rule: adapters depend on ports, never the reverse.

### Pattern 1: gqlgen.yml Field Resolver Configuration

**What:** Add `resolver: true` directives in `gqlgen.yml` under `models:` to force gqlgen to generate field-level resolver methods for relationship fields.

**When to use:** Always preferred over inline `@goField(forceResolver: true)` schema directives for this project (CONTEXT.md decision).

**Example (add to existing `gqlgen.yml` `models:` section):**
```yaml
# Source: https://gqlgen.com/config/ and gqlgen getting-started docs
models:
  Perspective:
    fields:
      user:
        resolver: true
      content:
        resolver: true
  Content:
    fields:
      addedBy:
        resolver: true
```

After `make graphql-gen`, gqlgen generates:
- `perspectiveResolver` type with `User(ctx, obj *model.Perspective) (*model.User, error)` and `Content(ctx, obj *model.Perspective) (*model.Content, error)` methods
- `contentResolver` type with `AddedBy(ctx, obj *model.Content) (*model.User, error)` method

These are added to the relevant `*.resolvers.go` files (gqlgen uses `filename_template: "{name}.resolvers.go"` — so `perspective.resolvers.go` and `content.resolvers.go` will be created or updated).

**Important:** gqlgen's `follow-schema` resolver layout creates one file per schema type. New files `perspective.resolvers.go` and `content.resolvers.go` will be generated. They must be implemented (not left as `panic("not implemented")`).

### Pattern 2: Loaders Package Structure (dataloadgen)

**What:** A single `loaders.go` file encapsulates the Loaders struct, per-request construction, context injection middleware, and helper accessor functions.

**Example (Source: https://github.com/vikstrous/dataloadgen-example/blob/master/graph/loader/loader.go verified against dataloadgen v0.0.10 API):**
```go
package loaders

import (
    "context"
    "net/http"
    "time"

    "github.com/vikstrous/dataloadgen"
    "github.com/CodeWarrior-debug/perspectize/backend/internal/core/domain"
    portrepos "github.com/CodeWarrior-debug/perspectize/backend/internal/core/ports/repositories"
)

type ctxKey string

const loadersKey = ctxKey("dataloaders")

// Loaders holds all per-request dataloaders
type Loaders struct {
    UserLoader    *dataloadgen.Loader[int, *domain.User]
    ContentLoader *dataloadgen.Loader[int, *domain.Content]
}

// NewLoaders creates a fresh set of loaders backed by the given repositories.
// Must be called once per request — loaders cache within request scope.
func NewLoaders(userRepo portrepos.UserRepository, contentRepo portrepos.ContentRepository) *Loaders {
    ur := &userBatcher{repo: userRepo}
    cr := &contentBatcher{repo: contentRepo}
    return &Loaders{
        UserLoader:    dataloadgen.NewMappedLoader(ur.batchUsers, dataloadgen.WithWait(time.Millisecond)),
        ContentLoader: dataloadgen.NewMappedLoader(cr.batchContent, dataloadgen.WithWait(time.Millisecond)),
    }
}

// Middleware injects a fresh Loaders instance into each request's context.
func Middleware(userRepo portrepos.UserRepository, contentRepo portrepos.ContentRepository) func(http.Handler) http.Handler {
    return func(next http.Handler) http.Handler {
        return http.HandlerFunc(func(w http.ResponseWriter, r *http.Request) {
            loaders := NewLoaders(userRepo, contentRepo)
            r = r.WithContext(context.WithValue(r.Context(), loadersKey, loaders))
            next.ServeHTTP(w, r)
        })
    }
}

// For retrieves the Loaders from context. Panics if middleware was not applied.
func For(ctx context.Context) *Loaders {
    return ctx.Value(loadersKey).(*Loaders)
}

// GetUser loads a single user by ID through the UserLoader.
func GetUser(ctx context.Context, id int) (*domain.User, error) {
    return For(ctx).UserLoader.Load(ctx, id)
}

// GetContent loads a single content by ID through the ContentLoader.
func GetContent(ctx context.Context, id int) (*domain.Content, error) {
    return For(ctx).ContentLoader.Load(ctx, id)
}
```

### Pattern 3: Batch Functions using NewMappedLoader

**What:** `NewMappedLoader` takes a `func(ctx, []KeyT) (map[KeyT]ValueT, error)` — returns a map instead of an ordered slice. The library handles key-to-value routing and automatically returns `dataloadgen.ErrNotFound` for keys missing from the map.

**Why NewMappedLoader over NewLoader:** GORM's `WHERE id IN` returns rows in database order, not input key order. `NewLoader` requires results in the exact same order as input keys — getting this wrong causes silent data corruption (wrong user returned for wrong perspective). `NewMappedLoader` eliminates this risk entirely.

**Example:**
```go
// userBatcher wraps UserRepository for dataloadgen
type userBatcher struct {
    repo portrepos.UserRepository
}

func (b *userBatcher) batchUsers(ctx context.Context, ids []int) (map[int]*domain.User, error) {
    users, err := b.repo.GetByIDs(ctx, ids)
    if err != nil {
        return nil, err
    }
    result := make(map[int]*domain.User, len(users))
    for _, u := range users {
        result[u.ID] = u
    }
    return result, nil
}

// contentBatcher wraps ContentRepository for dataloadgen
type contentBatcher struct {
    repo portrepos.ContentRepository
}

func (b *contentBatcher) batchContent(ctx context.Context, ids []int) (map[int]*domain.Content, error) {
    contents, err := b.repo.GetByIDs(ctx, ids)
    if err != nil {
        return nil, err
    }
    result := make(map[int]*domain.Content, len(contents))
    for _, c := range contents {
        result[c.ID] = c
    }
    return result, nil
}
```

### Pattern 4: GORM Batch Query (GetByIDs Implementation)

**What:** Standard `WHERE id IN` GORM query for fetching multiple records in a single SQL call.

**Example (for GormUserRepository):**
```go
// GetByIDs retrieves multiple users by their IDs in a single query.
// Source: https://gorm.io/docs/query.html — "WHERE id IN" pattern
func (r *GormUserRepository) GetByIDs(ctx context.Context, ids []int) ([]*domain.User, error) {
    if len(ids) == 0 {
        return nil, nil
    }
    var models []UserModel
    err := r.db.WithContext(ctx).Where("id IN ?", ids).Find(&models).Error
    if err != nil {
        return nil, err
    }
    users := make([]*domain.User, len(models))
    for i := range models {
        users[i] = userModelToDomain(&models[i])
    }
    return users, nil
}
```

Note: Returns `([]*domain.User, error)` — a single error for the whole batch. Per-key errors are NOT returned here; the batch function uses a map to signal missing items (via `ErrNotFound` from `NewMappedLoader`).

### Pattern 5: Chi Middleware Wiring in main.go

**What:** `r.Use()` accepts any `func(http.Handler) http.Handler` — the same signature as the `Middleware` function above.

**Example addition to `cmd/server/main.go`:**
```go
// After initializing repos and before route registration:
r.Use(loaders.Middleware(userRepo, contentRepo))
```

This must be placed AFTER `r.Use(middleware.RequestID)` but BEFORE `r.Handle("/graphql", srv)`.

**Important:** The repositories passed to `Middleware` must be the raw repository implementations (not the service layer) because dataloaders bypass the service layer — they fetch from the repository directly to avoid service-level N+1 logic that doesn't exist yet.

### Pattern 6: Field Resolver Implementation

**What:** Field resolvers call `loaders.GetUser()` or `loaders.GetContent()` instead of going through the service layer.

**Example (in generated `perspective.resolvers.go` after `make graphql-gen`):**
```go
// User is the resolver for the user field of Perspective.
func (r *perspectiveResolver) User(ctx context.Context, obj *model.Perspective) (*model.User, error) {
    userID, err := strconv.Atoi(obj.UserID)
    if err != nil {
        return nil, fmt.Errorf("invalid userID: %w", err)
    }
    domainUser, err := loaders.GetUser(ctx, userID)
    if err != nil {
        if errors.Is(err, dataloadgen.ErrNotFound) {
            return nil, nil // user deleted — return null gracefully
        }
        return nil, err
    }
    return userDomainToModel(domainUser), nil
}

// Content is the resolver for the content field of Perspective.
func (r *perspectiveResolver) Content(ctx context.Context, obj *model.Perspective) (*model.Content, error) {
    if obj.ContentID == nil {
        return nil, nil // optional relationship — no contentID set
    }
    contentID, err := strconv.Atoi(*obj.ContentID)
    if err != nil {
        return nil, fmt.Errorf("invalid contentID: %w", err)
    }
    domainContent, err := loaders.GetContent(ctx, contentID)
    if err != nil {
        if errors.Is(err, dataloadgen.ErrNotFound) {
            return nil, nil
        }
        return nil, err
    }
    return domainToModel(domainContent), nil
}
```

**Note:** `obj.UserID` in the generated model is a `string` (it's a GraphQL `ID` scalar mapped to `graphql.ID`). It requires `strconv.Atoi` to get the `int` key for the loader — consistent with existing patterns in `schema.resolvers.go`.

### Anti-Patterns to Avoid

- **Singleton loaders:** Loaders MUST be created per-request. If created once at startup and shared, the request-scoped cache causes cross-request data leaks and stale data. The middleware creates a new `Loaders` instance on every incoming request.
- **Using `NewLoader` with GORM:** GORM's `WHERE id IN` does not guarantee result order matching input key order. Always use `NewMappedLoader` when results may be unordered.
- **Calling services from dataloaders:** Dataloaders should call repositories directly, not services. Services may have additional logic (like calling other services), which could re-introduce N+1.
- **Empty IDs slice to GORM:** Always guard with `if len(ids) == 0 { return nil, nil }` before calling `db.Where("id IN ?", ids).Find(...)` — GORM generates invalid SQL for empty slices.
- **Placing loaders in domain/services:** Dataloaders are infrastructure (adapter) concerns, not domain concerns. They must live in `internal/adapters/graphql/loaders/`.

## Don't Hand-Roll

| Problem | Don't Build | Use Instead | Why |
|---------|-------------|-------------|-----|
| Request deduplication | Custom sync.Map per-request cache | `dataloadgen` caching (built-in) | Race conditions in concurrent field resolvers, complex invalidation |
| Batching window | Custom time.Sleep + goroutine | `WithWait(time.Millisecond)` option | Subtle goroutine leaks, missed batches, off-by-one timing |
| Result ordering | Manual index tracking for ordered results | `NewMappedLoader` | Silent data corruption bugs when GORM returns out of order |
| Context propagation | Custom context key type + package global | `ctxKey` typed string key (built-in pattern) | Type collision with other packages using plain string keys |

**Key insight:** The batching window logic is genuinely tricky — DataLoader waits a configurable duration before firing a batch, but must also fire immediately if a resolver goroutine is the first after the previous batch cleared. Getting this timing right without library support leads to either missed batches (defeating the purpose) or excessive latency.

## Common Pitfalls

### Pitfall 1: Mock Compilation Break on Interface Update

**What goes wrong:** Adding `GetByIDs` to `UserRepository` and `ContentRepository` port interfaces immediately breaks compilation of all mock implementations in `test/resolvers/content_resolver_test.go`. The `mockUserRepository` and `mockContentRepository` structs do not implement the new method.

**Why it happens:** Go's interface compile-time check. The CLAUDE.md Gotchas section explicitly calls this out: "When adding a new method to a port interface, all test mocks that implement that interface must also be updated or compilation fails."

**How to avoid:** Add `getByIDsFn func(ctx context.Context, ids []int) ([]*domain.User, error)` stub field AND the method implementation to BOTH mock types immediately when updating the interfaces. Do this before running any tests.

**Warning signs:** `cannot use mockUserRepository as type repositories.UserRepository in assignment` compile errors.

### Pitfall 2: Perspective.User Resolver Receives model.Perspective with string UserID

**What goes wrong:** The generated `perspectiveResolver.User()` method receives `obj *model.Perspective`. The `obj.UserID` field is `string` (GraphQL `ID` scalar). The UserLoader key is `int`. Forgetting `strconv.Atoi` causes a compile error or type mismatch.

**Why it happens:** gqlgen maps `ID!` in the schema to `string` in Go model structs. This is consistent with every other resolver in `schema.resolvers.go` that calls `strconv.Atoi(id)`.

**How to avoid:** Always `strconv.Atoi(obj.UserID)` before calling `GetUser(ctx, userID)`. Handle the error (malformed ID would be a programming bug, not a user error).

### Pitfall 3: setupTestServer Doesn't Inject Loaders into Context

**What goes wrong:** The existing `setupTestServer` in `test/resolvers/content_resolver_test.go` creates an `httptest.Server` that wraps the gqlgen handler directly without any middleware. Field resolver tests calling `loaders.For(ctx)` will panic with a nil pointer dereference when they try to cast `nil` from context.

**Why it happens:** The middleware that injects `*Loaders` into context isn't applied in the test server setup.

**How to avoid:** Either (a) wrap the gqlgen handler with `loaders.Middleware(mockUserRepo, mockContentRepo)` inside a new `setupTestServerWithLoaders()` helper, or (b) extend the existing `setupTestServer` to accept an optional loader factory. The mock repos passed to the middleware must be the same mocks used for the services so test assertions can check both.

**Warning signs:** `panic: interface conversion: interface {} is nil, not *loaders.Loaders`.

### Pitfall 4: dataloadgen Default Wait is 16ms (Not 2ms)

**What goes wrong:** Documentation and CONTEXT.md say "default 2ms" but the actual source code default is `16 * time.Millisecond`. Tests that depend on timing (e.g., testing that a batch fires after waiting) may use the wrong constant.

**Why it happens:** The CONTEXT.md mentioned "Default 2ms wait time for batching" — this is incorrect. The verified default from the dataloadgen source code is 16ms.

**How to avoid:** Always pass explicit `dataloadgen.WithWait(time.Millisecond)` to tests that need predictable batching timing. For production use, 1ms wait is appropriate for low-latency servers.

**Warning signs:** Tests that assert "batch fires within Xms" that intermittently fail.

### Pitfall 5: ContentID is Nullable — Content Field Resolver Must Check nil

**What goes wrong:** `Perspective.ContentID` is an optional FK (`*int` in domain, `*string` in model). If a Perspective has no associated Content, the field resolver must return `nil, nil` without calling the loader. Calling `loader.Load(ctx, 0)` or passing `nil` as a key will return wrong results.

**Why it happens:** The `model.Perspective.ContentID` field is `*string` — it's nil when not set. The resolver receives `obj.ContentID = nil`.

**How to avoid:** Guard at the top of `Content()` field resolver: `if obj.ContentID == nil { return nil, nil }`.

### Pitfall 6: gqlgen Regeneration Moves Resolver Code

**What goes wrong:** After adding field resolver directives and running `make graphql-gen`, gqlgen creates new files (`perspective.resolvers.go`, `content.resolvers.go`). If any code in `schema.resolvers.go` has manually added content for these types, gqlgen may move it or conflict.

**Why it happens:** gqlgen with `follow-schema` layout creates one file per schema type name. Running generate after adding field resolvers creates new resolver files.

**How to avoid:** Let `make graphql-gen` run first, then implement the generated stub methods. Do not pre-write the resolver functions before generating.

## Open Questions

1. **Resolver file naming after `make graphql-gen`**
   - What we know: gqlgen `follow-schema` layout creates `{name}.resolvers.go` per schema type. Adding field resolvers for `Perspective` and `Content` types should create/update `perspective.resolvers.go` and `content.resolvers.go`.
   - What's unclear: Whether gqlgen creates new files or appends to the existing `schema.resolvers.go` — depends on whether gqlgen treats all types as the "schema" source.
   - Recommendation: Run `make graphql-gen` after updating `gqlgen.yml` and inspect which files are created/modified before implementing. The existing `schema.resolvers.go` header says "This file will be automatically regenerated" so gqlgen manages file location.

2. **Should `Resolver` struct hold repository references for loaders?**
   - What we know: The `Resolver` struct currently holds services. Loaders need repositories, not services. The `Middleware` function in `loaders.go` takes repos directly.
   - What's unclear: Whether `main.go` needs to pass repos to both `loaders.Middleware()` AND `services.New*Service()` separately, or if a cleaner abstraction exists.
   - Recommendation: Pass repos directly to `loaders.Middleware()` in `main.go`. This is clean because loaders are middleware concerns, not resolver concerns. The `Resolver` struct does not need to change.
